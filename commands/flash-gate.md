Apply phase 3 of the `linux-phone-porting` skill to: $ARGUMENTS

**First: refresh the session's task list** — replace whatever is there with this command's steps, one item per step, first step in progress (`SKILL.md` chain rule).

`SKILL.md` phase 3 owns the rules this gate enforces — authorization scoping, physical limits, one-variable discipline, the pre-build battery, the deployment state machine, cleanup and completion records. This command is the six-question gate and its routing; it does not restate the rules.

**Precondition:** phase 0 identity, verified backup and demonstrated recovery/control capabilities are available, and phase 1 evidence or phase 2 capability research backs this change. Missing prerequisites return to their phase commands. Immediately before every device write, re-enumerate, pin the transport, reconcile target identity and active boot target with the intended artifact, and stop on ambiguity.

**Safety precondition for every experiment, not just a flash:** apply the skill's scoped authorization, pause, private-calibration and protection gates. For physical output, record limits with units, duration, stop conditions and final safe state; verify enforcement on the actual path. A passing hypothesis gate cannot authorize bypassing limits, increasing stress without proven observability, using guessed calibration or wiping excluded userdata.

Answer each of these before anything is written to the device. Any "no" blocks the flash.

1. **What is the hypothesis?** State it as a falsifiable sentence — what is broken, why this change addresses it, and what the device will do differently if it is right.
2. **Which source backs it — and when was it found?** Name the evidence or the research finding, and say which research pass produced it. "It seems likely" is a refusal; so is a source that only comes from the ledger of earlier iterations when the current framing differs from theirs — after a refutation the backing must come from a pass that ran against the refuted framing, not the one it killed. A design derived from the vendor driver source or the stock DTB passes — naming the artefact is naming the source — but a _newly read_ part of it, not the paragraph a previous hypothesis already leaned on. No applicable precedent found in the searched projects is not a refusal; retain the coverage and access gaps and derive from primary evidence.
3. **Is this one variable?** If the change touches more than one thing, split it. Keep a project/layout move separate from a kernel or OS upgrade: first compare the old and moved kernel, DTB, modules, firmware and initramfs payloads and downstream image-assembly inputs and outputs. Matching payloads alone do not prove an unchanged final boot image. A passing multi-variable flash teaches you nothing about which part worked.
4. **Can it be tested without a flash?** Push files with a tar pipe, unbind and rebind the driver, `insmod` the module, rebuild only the DTB. Seconds beat minutes; take the cheap test if one exists. A probe module leaves state — a failed init can cost a reboot per retry, and a crashed one can wedge the board — so stage its inputs, verify their hashes host-side, and expect one reboot per failed attempt.
5. **How many fixes have been refuted on this symptom?** Under `/port-loop`, the operator's refutation budget (5, 15, or unlimited, set at invocation) governs — the loop keeps going while budget remains. Standalone, past three the same-layer model is dead: do not flash a fourth tweak from it — widen the scope and re-enter `/source-sweep`, because the model of the failure is what is wrong.
6. **What result would refute this?** State the falsifier — the smallest experiment whose result kills the plan either way — and decide it now, so the next boot's dmesg is read honestly rather than for confirmation. Run the cheapest experiment that produces that result before flashing anything larger.

**If the change requires a full rebuild** — the most expensive step in the loop — run SKILL.md's pre-build battery first: `find-docs` the kernel/image/update tooling (current flags, not recalled; `mkbootimg`/`mkdtboimg` bind their formats only), then pristine checkout, series-order patch applies, symbol/Kconfig/compile-alone checks. A build that dies 15 minutes in on a missing symbol is a check that was skipped, not bad luck. The edits feeding it must be clean per SKILL.md's edit-and-hope rule — a previous edit being "fixed" is redone from a fresh read, never patched over.

**Apply and observe.** With all six passed and safety prerequisites intact: cheapest authorized decisive experiment; record the outcome against the hypothesis as stated, including what a refutation rules out. Reboots through demonstrated channels, operator-hands boundaries, observable-result verification (disappearance is ambiguous; poll briefly, re-ask within a bound) and pause handling follow SKILL.md's operator-hands rules.

**Read the runtime surface the change was meant to move.** A DT that builds can bind to nothing; a session/compositor swap re-opens layer defaults — run SKILL.md's session-swap checks. Deployment states (transfer, next-boot selection, activation, observed reboot) follow SKILL.md's state machine; transport/service readiness is recorded separately from end-to-end acceptance. Capture before/after metrics under the same controlled conditions through `/evidence-sweep`, verify the agreed final safe state, and reconcile completion/authorization records without deleting history. Target met with an unexplained new fault is not clean integration.

**Post-upgrade cleanup is gated by a verified reboot and required runtime checks** — then follow SKILL.md's cleanup rule: inventory disk use including generations/roots, preserve the running system and the complete rollback set, archive historical images/symbols/logs host-side, remove only explicitly identified deployments through the supported mechanism, record space and reclamation, and never attribute GC savings to old kernels without separate accounting.

**If the defect is shared**, prepare the portable upstream report per SKILL.md's security-findings rules — exact base/patched revisions, captured reproduction with boundary conditions, the publication-hygiene sweep over the report before it leaves the project, a CVE cited only when source and preconditions match, submitted/accepted/merged/released as distinct states — and hand it to `/port-upstream` for destination research and the user-owned submission gate.

**Then** route the recorded outcome yourself — the gate does not end at "experiment done": a refutation with budget remaining names the next hypothesis and re-enters research (wider, after three); a passing experiment proceeds to the verification, acceptance and cleanup gates above and reports against the original target sentence; a shared defect goes to `/port-upstream`. If the only remaining actions need the operator — physical hands, a destructive write outside the backup's coverage, a pause — say precisely what and why, and stop there.
