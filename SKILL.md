# Linux Phone Porting

A debug iteration costs a build + flash + boot (5-10 min); blind fixes get refuted far more often than they land. Follow this order strictly.

## 0. Set up the port

Once, before the first flash. Rationale: the stock system is the highest-authority research source for this board, and parts of it stop being readable once overwritten.

**Establish the target** (every later answer depends on it):

- **Exact device identity** — marketing name, codename, SoC, regional/storage variant. Sibling variants of the same name routinely differ in panel, touch controller, modem; a fix researched against the wrong variant looks plausible and fails. Record sibling codenames/model numbers — phase 2 enumerates their ports.
- **Engineering stage** — EVT/DVT/PVT revision where exposed, board identity, carrier/SKU, bootloader product + build fingerprints. Reconcile disagreements before selecting sources/images: a presumed retail handset was an EVT board for a different product while Android still reported `user/release-keys`. Build labels do not establish production hardware.
- **Target distro and init** — postmarketOS, Mobian, NixOS, plain Debian, other. Decides packaging, image layout, closest phase 2 source.
- **Target userspace shell** — ask the user; never assume a default. If the target OS ships its own shell (e.g. a UBports port), strongly recommend it — fighting the distro's compositor/session stack costs on every rebuild.
- **Boot topology** — A/B or not, slot layout, bootloader lock state. On A/B, decode slot state from the on-disk structure, not documented layouts (one SoC kept it in GPT partition-entry attribute bits, not the documented bootloader-control partition). After a crash-loop, refill the tries-remaining budget (nothing marks the slot successful there) before interpreting the next failure. **Unlocked bootloaders only** — this skill does not unlock or give unlocking steps; point the user at the OEM's own instructions and resume when unlocked.
- **Recovery** — custom recovery installed? A convenience, not a requirement.

Vendor A/B bank names do not establish seamless-update/slot-control/fallback semantics — establish the implementation before manipulating banks. Empty security properties = unknown, not unlocked. Same-SoC trees/firmware/signed recovery programmers are candidates, not certified recovery paths; an unreleased prototype's only installed system may have no compatible replacement — preserve it, get a restorable backup before destructive experiments.

**Back up every partition except userdata:**

- Skip userdata: bulk of space, user's data, the one partition you can afford to lose (leave a DO-NOT-RESTORE note for it inside the backup).
- **Device-unique partitions — back up, never publish.** Modem NV/EFS, persist, calibration siblings carry IMEI, radio calibration, sensor trim; unreproducible from any image; corrupting them leaves a phone that cannot register on a network. Critical AND private.
- Hash every image; record hashes beside the partition table. Only a hash answers "is the device still what I backed up".
- Verify restorable before the first risky flash, not after.
- **EDL (emergency download) is the fallback backup route when boot-based channels cannot read partitions — prove the channel, don't assume it.** A signed firehose programmer (OEM EDL package or community custom ROM EDL bundle) grants raw storage; its rawprogram XML doubles as an independent partition-map cross-check against the on-device GPT. Programmers are per-variant revisions; a mismatched one can configure cleanly and still not stream.
- **A bulk dump loop stops at the first zero-byte or short read and treats it as fatal.** A run whose partition-table read itself returned zero bytes still recorded per-partition failures for the whole list. Probe the smallest read (the GPT) first; diagnose the loader/programmer variant instead of iterating a void list.

**Research value of the backup, beyond recovery:**

- **Stock DTB** — ground truth for this board's device tree; the tiebreaker when the sibling SoC's dtsi disagrees.
- **Firmware blobs + load order** — what the vendor stack ships and where it looks for it.
- **Vendor kernel cmdline + boot image layout** — offsets, header version, arguments.
- **Exact kernel version string** — `uname -a` or `/proc/version` from the stock ROM while readable (also unpackable later from the backed-up boot image). This fingerprint selects the right GPL-published OEM source release in phase 2; vendors ship several builds and they differ.
- **Vendor configs** — sensor, modem, HAL: the interfaces the mainline driver must satisfy.

**Check storage health before trusting device reports:**

- **Read and record the storage's wear/lifetime report in phase 0** (UFS life-time percentage, eMMC health register — whatever it exposes). Storage is the classic misdiagnosis: I/O errors read as a dying drive, the wear percentage proved it healthy, the real fault cleared with one more fastboot flash of the stock ROM. The percentage separates "hardware dying" from "software state bad" — opposite next steps.
- A media-failure verdict that would retire the device must survive a **re-probe in a later session** before it drives that decision: one port recorded a flash region refusing writes twice, cold power-off included; the same write passed three of three the next day against a full zero-error read scan. Absent wear fields = health unknown; coarse wear values do not exclude other faults. The healthy-storage finding overturned one wear diagnosis, not every failure mode.

**Inventory + harvest the stock system while present:**

- **Inventory every component the stock system names** — panel, touch controller, sensor set, camera sensors, modem + RF config, WLAN/BT chip, charger + fuel gauge, audio path — and compare against this variant's official spec sheets: invoke the `find-docs` skill for component documentation, `wigolo` for spec sheets and anything web-found (its cache matters — these pages get re-read across sessions of the same port); if neither is installed, plain web search. Sibling variants differ exactly here; the comparison catches "researched the wrong variant" before it costs a flash.
- **Evidence level** — label each capability declared / enumerated / driver-bound / exercised. A HAL name can reflect software ancestry, not silicon; installed firmware may support an unfitted component. One camera advertised 1080p30 in USB descriptors while Android exposed at most 1024×768 and 27 fps; no frames captured, so throughput was never measured.
- **Rooted stock beats a ROM image as a source.** A backup preserves bytes; root keeps the system running and readable: `getprop`, stock kernel config (`/proc/config.gz`), mounted vendor/odm trees, HAL/sensor configs, calibration artefacts, factory field-test modes. Assume the user roots it themselves; like bootloader unlocking, provide no rooting steps — one wrong step bricks — and resume when root is available.
- **Record the newest community custom ROM as an optional, up-to-date development source.** Ask whether recent custom ROMs exist and where they live. Measured: the most responsive OS ever run on one device was an unofficial recent-Android custom build, not stock — and its boot image shares the stock downstream lineage, so its DTB cross-checks the phase 0 extraction. An EDL package bundled with a port also carries the signed firehose programmer + rawprogram map — fallback backup route and independent partition-map source.

**Working conventions.** Resolve the **device project root** first. For a multi-device workspace this layout is the reference, not a restructuring order:

```text
kernel/<version>/     Clean upstream source + generic builder
soc/<vendor-soc>/     SoC-common patches, configuration and packages
os/<distro>/          Device-neutral OS integration and tools
devices/<model>/      Device assembly, patches, calibration and state
```

Shared bases never import device policy; put changes in their owning layer; device facts, private captures and per-device agent context stay with the device. Mark a shared kernel tree used for experiments as patched, never mistake it for pristine upstream.

- **Project layout.** Everything large, private, or device-derived lives under `artifacts/` at the **device project root** — gitignored, never committed, never unignored — classified: `private/` (device-unique, never leaves the machine; the partition backup first of all), `firmware-harvest/` (blobs pending redaction), `android/` (reproducible stock-ROM packages, rooted captures), `debug-evidence/` (irreplaceable captures, preregistrations), `reference/` (reading copies of upstream sources). Publishable firmware goes to a sibling `firmware-publishable/` repo with its own git history, derived from the harvest only after redacting device-unique identifiers. Device-local `logs/`: one subdir per boot/deploy + `LATEST-*` symlinks. A README in `artifacts/` maps every path to its class and records hashes, acquisition method, coverage — provenance, not a substitute for integrity checks.
- **Device control channels.** Before any flash, prove reachability: host `adb` + `fastboot` exercised against this device, plus at least one post-boot channel into target Linux (USB-gadget Ethernet, serial ACM console, ssh over network/USB). Record which channels work + addresses; a channel assumed but never tested is discovered missing mid-wedge — the worst time.
- **Bind every operation to the target.** Record handset↔transport mapping; explicitly select the transport for every command; re-establish after re-enumeration; verify product + slot immediately before writes. A second connected phone must never become an implicit target; keep identifying captures private. The binding constrains the **host** too: a reachability probe must never mutate host network config. A successful ping is not target identity; a name-based fallback can reconfigure the wrong interface — one absent gadget MAC made a control script rewrite an unrelated USB Ethernet dock's IP settings. Inspect interface identity + route first, refuse missing/ambiguous matches, make host network setup a separate explicit command on an owned, uniquely verified interface.
- **Prove the operation, not just the connection.** Record whether required backup/loading operations are actually supported before building around them. One unlocked bootloader supported neither RAM boot nor partition fetch, stranding a built rescue image. Unsupported operations are not permission to flash an unverified image; research a non-destructive route. Support goes deeper than the handshake: a firehose that connects, configures and advertises the full `read` command set still truncated every streamed read to 16 bytes of a 17,408-byte request — stock tool and two custom driver revisions alike. An advertised command list is not a working data path; self-test-read a small region of known content and verify returned bytes, not just the acknowledgement, before scripting bulk transfer.
- Note which recovery path is known to work.

Write into the project's agent context files (`CLAUDE.md`, `AGENTS.md`, equivalents): all work touching this device goes through this skill's ruleset; no device action outside it. If a backup already exists from an earlier attempt, confirm coverage + that hashes still verify — don't assume.

**Keep a bootable Android around for data gathering.** While stock or a rooted custom ROM boots, it stays an evidence channel: read a working vendor driver's probe/firmware sequence live next to a mainline failure; exercise hardware mainline cannot yet drive to prove the silicon is fine. A mainline boot failure never forbids an Android boot for data — only concluding anything about mainline behaviour from Android behaviour without a cross-check.

## 1. Gather evidence from the live device first

Capture the failing run's full dmesg before changing anything. Enable debug knobs _before_ reproducing (e.g. `echo 0xffffffff > /sys/module/<driver>/parameters/debug_mask`) — a second reproduction costs another boot.

Interpreting evidence is kernel work: invoke `linux-kernel-development` if installed, else `linux-kernel-crash-debug`, else any subsystem-specific kernel skill — dmesg reading, debug-knob choice, probe/ramoops/pstore interpretation all need its register-level detail. If none installed, reason from kernel sources + `Documentation/` directly; do not stall.

### Record acquisition and claim boundaries

Per artifact, record origin (live capture/archive), exact revision/build, acquisition method, coverage, access failures, integrity hashes. A running sysfs device tree may include runtime fixups — it is not an untouched boot-image DTB. One capture preserved 2,740 property files, verified 2,222 byte-identical, accounted for 518 redundant name properties; all 2,839 manifest files passed integrity checks — still not a restorable partition backup. A firmware path inventory does not establish load order.

Carry phase 0's declared/enumerated/driver-bound/exercised labels into findings. Record running vs deployed identities separately; distinguish service readiness from end-to-end hardware behaviour. A registered sound card + successful silent playback do not establish acoustic qualification; mark listening/full-power/headset/microphone checks untested when not exercised.

### Evidence channels, roughly by reliability

- **Live shell over network or USB.** Cheapest; use for anything the device survives.
- **A still-bootable Android.** Boot deliberately when a question is best answered there: vendor driver probe/firmware sequence live next to the mainline failure; exercise hardware mainline cannot drive. Never conclude about mainline from Android without a cross-check.
- **pstore.** Once systemd is up, harvest from `/var/lib/systemd/pstore/`, **not** `/sys/fs/pstore/` — `systemd-pstore.service` moves every record out early in boot; an empty `/sys/fs/pstore` is not evidence that no crash was recorded. The console region is typically a single slot: copy it to the host first, or the next crash overwrites it in the archive too.
- **ramoops.** Lossy. DRAM charge retention decays across the unpowered interval — measured ~6.5 % of bits on one device, enough to fail ECC on zone headers and lose a record entirely — and warm reboots rot the region too (tens of blocks measured): decay follows the power cycle, not just the unpowered interval. Grep records _fuzzily_. Time unpowered rots the region, not time spamming before power cut — let a wedged device log as long as the console zone holds, then power-cycle and back promptly. Check zone size before hurrying: a 4 MiB console zone absorbs hours of watchdog spam before wrapping.
- **Kernel-level USB ACM console** (`CONFIG_U_SERIAL_CONSOLE=y` + `console=ttyGS0`). The only channel that survives a wedge — but verify it survives the _reporting context_ before spending the flash: the payload is emitted inside `panic()` with local IRQs off and other CPUs stopped; a console whose write path defers to a workqueue cannot run there — facility arms, messages never print. Test free first with a kernel crash injector (where present, LKDTM `/sys/kernel/debug/provoke-crash/DIRECT`): deterministic synthetic lockup, exact reporting geometry, no flash. A _userspace_ ACM getty does not survive either — needs a schedulable CPU, yields zero bytes while still enumerating fine. Both config halves required; the symbol alone leaves the facility inert.

### Rules that turn inference into measurement

- **Confirm what is flashed by reading the partition back** — never notes or build logs. Read with `iflag=direct` so the read doesn't perturb the debugging. Size-only comparisons prove nothing (boot images are padded to fixed size). Hash the payload.
- **Reading a debug interface can manufacture the symptom.** Sampling DRM/GPU crash-state nodes during active GPU submission synthesises fault/recovery lines that never occurred (measured: five reads, five fault/recover pairs; none unobserved). Before trusting a log line, check whether your own observation produced it.
- **A status register that never changes under stimulus is a latch, not telemetry.** Establish liveness with a value known to change: one camera link read status bytes byte-identical with transmitter on and off — only that proved the bank static rather than the link healthy.
- **Capture a rejection's raw response before interpreting the mapped errno.** A firmware `EINVAL` was ambiguous — wrong encoding or refused policy — until dynamic debug exposed the raw response words: a well-formed call carrying explicit refusal. Policy, not encoding — opposite verdict, opposite next step. Classify every firmware rejection: wrong encoding / refused by policy / not found — before acting. Mirror rule: a clean, well-formed negative is positive proof — a not-found from a correctly-formed lookup validates the encoding and eliminates a plan branch without touching the loader.
- **A measurement racing an uncontrolled condition returns a plausible, void number.** One benchmark scored 55 in two seconds — the compositor held DRM master, every scene failed, the number looked real until the condition was checked. The valid comparison, 132 → 485, needed the compositor stopped for both runs. Name the condition that could void a benchmark; verify it held for every run.
- **Record the rules you withdraw.** Bring-up accumulates folklore; a rule right for one hardware revision or buffer size becomes actively misleading after it changes. Keep the overturned version next to the current one with what changed — the next session needs to know which advice is stress-tested.

### Host-side gotchas

- `timeout N ssh <device> '<cmd>'` kills the local client only; the remote process keeps running — follow up with an explicit kill.
- `pgrep -f`/`pkill -f` over that ssh path **self-match** their own remote shell. Filter the matcher out, or match by PID.
- `find` needs `-L` when the start path is a symlink, or it returns silently empty.
- Any wrapper/hook that rewrites command output — token filters, pagers, formatters — corrupts evidence, sometimes inverting a test rather than obviously breaking it. Use the raw command for anything committed as a finding.

### Operator hands are a step, not an assumption

- **When a step needs a physical action** (moving media, replugging, holding buttons, confirming on-screen), name the exact action + direction ("move the SD card from host to phone"), then **verify it happened before continuing** — an observable signal, not the fact you asked. The signal can be an appearance (mount appears, USB re-enumerates, slot changes) or a **disappearance** (device powers off, USB drops, channel goes silent). Disappearance is ambiguous — "not done yet" and "done, device off now" look identical to a poller: watch the channel closely when the action is due so the drop is caught as an event; where it can't be watched, require operator confirmation + a verified post-absence probe failure. Never wait passively: poll on a short interval; no signal within a stated bound ⇒ re-ask. Sessions lose minutes to hours either way.
- **Total channel loss after suspend/resume has three branches, not two.** From the host, live-phone-with-dead-driver is indistinguishable from hung/dead — one port's "suspended and never came back" was wrong: suspend/resume worked and ran another 10.5 hours; only the USB gadget failed on resume (`HS-PHY not in L2`). After a replug, read the device's own journal from its last boot before declaring a hang — "it died" vs "it survived but its driver did not" have opposite next steps.

## 2. Research before implementing — all of these sources

Research always precedes implementation. Input depends on the task:

- **Investigating a failure** — phase 1 evidence. Capture it first; researching a symptom you haven't read is guessing with citations.
- **Adding a capability** (never-seen driver/peripheral/subsystem) — phase 0 artefacts are the device data: stock DTB, vendor configs, firmware layout describe how the board expects the thing driven — as authoritative as a crash log.

Either way, **before** writing anything:

1. **Reason about the subsystem** — identify the driver, binding, or firmware interface that owns the failure (or would own the capability). Invoke `linux-kernel-development` if installed, else `linux-kernel-crash-debug`, else any subsystem-specific kernel skill. If none resolves, reason directly; do not stall. Invoke `find-docs` for the kernel-side docs — DT binding + dt-schema, Kconfig options/deps, subsystem docs — for the **exact kernel version being built**, not a recalled one; if not installed, read `Documentation/` in the tree. A binding constraint or Kconfig gate from memory is a guess; stale bindings and renamed symbols are what phase 3's rebuild-check battery catches late.
   **Indexed local navigation is optional.** Invoke `graft` when installed + repos indexed, to locate implementation and trace dependencies across kernel/SoC/OS/device layers; verify decisive details against the exact source revision. An index miss is not proof support is absent: check coverage, then direct source search, LSP navigation, file reads. Missing tooling never blocks research; graft navigates, it is not an evidence source.
2. **Look up userspace libs and tools** — current docs, not recalled API. `find-docs` per library/tool; if not installed, read the project's current docs over the web.
3. **Web research across every source family** (parallel subagents work well). Invoke `wigolo` for the sweep — its cache matters, sessions re-read the same pages; if not installed, plain web search. All of these, in order:
   - **The SoC vendor's mainline collaboration project** — for Qualcomm, [github.com/qualcomm-linux](https://github.com/qualcomm-linux). The vendor publishing mainline-first kernel work itself: updated dtsi, bindings, subsystem enablement, tooling, often ahead of the nearest mainline tree. Check before treating a missing node/driver as work you must author — the vendor may have landed it; its trees show how the vendor intends the hardware driven under mainline, the most authoritative template there is.
   - **Downstream vendor kernel — the GPL-published OEM source.** GPLv2 obliges OEMs to publish shipped kernel sources; an exact release for this device usually exists: the OEM's open-source portal (Samsung, Sony, Xiaomi, Fairphone, OnePlus/OPPO, Motorola all run one), their GitHub/GitLab mirrors, community archives such as XDA when a portal link died. Select the tarball whose version string matches phase 0's `/proc/version` — vendors publish several, they differ. Compliance quality varies: treat the tree as an oracle to mine (this device's board dts + defconfig; out-of-tree vendor drivers — touch, panel, charger, modem glue — with register sequences and firmware handshakes), not as something that builds. No exact release? A sibling device's usually still carries the SoC dtsi. Better still: **the stock DTB pulled off the device** (`dd` the untouched boot slot, scan for `d00dfeed`, `dtc -I dtb -O dts`) — ground truth for _this_ board, has corrected wrong sibling-SoC guesses more than once, including a SMMU stream ID the sibling SoC got wrong and the stock DTB got right.
   - **AOSP / Android platform source** — [android.googlesource.com](https://android.googlesource.com/), [source.android.com](https://source.android.com/): HAL interfaces, framework/services, init + VINTF config, SELinux policy, boot-image tooling, shared native libraries. Select branch/tag, record exact revision. Platform contracts complement, not replace, the exact OEM source + stock DTB + proprietary vendor implementation for board-specific behaviour.
   - **postmarketOS** — pmaports device packages + APKBUILDs, merge requests, wiki device pages, SoC-mainline tree.
   - **Halium / UBports** — `halium/android_device_*` trees, `hybris-boot` configs, UBports device ports. Best source for how the _vendor firmware_ expects to be driven: blob paths + load order, properties + sockets daemons expect, sensor/modem HAL configs. When a mainline driver probes but the firmware handshake fails — or you need the handshake a not-yet-supported peripheral expects — this is usually where it's written down.
   - **Mobian** — the Debian device repos.
   - **NixOS** — mobile-nixos patterns and nixpkgs packaging.

**Verify what you already carry against every downstream DT you hold.** Patches go stale against new ground truth: one port re-verified its set against the newest stock OTA DT, the original phase 0 backup, and a custom ROM tree — four patches confirmed, one CPU-capacities discrepancy no single source would have shown. Read the vendor flash script before trusting it: at least one ships slot-blind, hard-coding the wrong system image for the active slot.

- **Sweep sister devices, not just this one.** In those sources, enumerate ports of the same family — sibling models under the same marketing name (codenames phase 0 recorded) and near-neighbours on the same board/SoC generation; they surface in pmaports device pages, Halium/UBports trees, XDA forums, and the OEM kernel tree's own `dts/`. Diff each port's board files — dts, defconfig, firmware blob lists — component-by-component against the phase 0 inventory: a match = a proven driver+firmware combination to adopt; a divergence = where the family split, itself a hypothesis. The comparison is also the guard — a sister device is a lead, not a precedent. Adopt only what the diff confirms against this variant's spec sheet + stock DTB: siblings differ exactly in panel, touch, modem.

**Search internal product codenames and OEM/ODM archives too.** An extracted alternate-system image can reveal vendor implementation under a name absent from retail documentation. Preserve archive provenance; inspect board identity, configuration, firmware lineage. Archive contents are not evidence the handset runs the image, that it is compatible, or that flashing authorization and recovery exist.

### Security findings exposed by bring-up

- **A bulletin is not proof of a fix in your tree.** Compare advisories, available fixing commits, upstream implementation, AOSP against the exact revision being built; map source to executed binary where possible. One FastRPC investigation reproduced an unchecked DSP-length parsing path against a recent AOSP release despite an older bulletin describing the class. Similar mechanism + affected-chip list ≠ exact CVE identity; qualify attribution until technical evidence or maintainer confirmation.
- **Firmware data crosses a trust boundary.** Trace raw length words, decoding, signedness, arithmetic, cursor advancement, copy bounds before blaming firmware or hardware. One listener crash combined an unchecked decoded length with a remaining-space calculation that narrowed and wrapped positive. Protocol desync may explain malformed input; it never justifies unsafe parsing.
- **Make the shared defect reproducible upstream.** Reduce to the real parser + smallest portable reproducer, not a handset-specific workaround. One gate exercised five lengths — captured value, remaining space + 1, `0x7fffffff`, `0x80000000`, `0xffffffff` — SIGSEGV before fix, containment after. Submit affected revisions, field evidence, reproduction prerequisites, minimal patch, before/after results to the owning project's appropriate channel. Redact identifiers/private material; follow its disclosure policy. Record submitted/accepted/merged/released separately — a report or PR is not evidence consumers have the fix.
- **Thin results are the normal case, not a blocker.** Most of what a port needs has never been done on this board, often not the SoC. Every source reporting nothing = nobody has published the work — never a reason to stop or hand back. When precedent is absent, the answers are in the primary artefacts: the out-of-tree vendor driver already driving the peripheral (register sequences, firmware handshake, GPIO/regulator wiring), the stock DTB's node for it, the vendor HAL config naming what userspace expects, the closest mainline driver for the device class as structural template. Read, derive, write the missing piece — DT node, quirk, small driver. Authoring it is the ordinary terminal state of bring-up, not an exception to justify; the phase 0 backup + one-variable-per-flash exist precisely so a wrong derivation costs one boot and one ledger line.
- **An empty sweep and an empty scan are different findings.** Empty sweep = nobody published the work. Empty _scan_ (extraction returns nothing) = void until the same method ran against a known positive with coverage verified: file counts, segment lists, what the glob actually matched. Measured near-misses: a glob matched 9 of 27 firmware segments and nearly recorded a false "the firmware omits it"; a library scan became trustworthy only once it found a known chip id as positive control.
- **Downstream identifiers are downstream's private numbering.** An id/enum in the vendor tree is that tree's bookkeeping — never copy it into a mainline node. One downstream thermal trip pointed at "sensor 5"; on mainline sensor 5 read constant 0 and the real tracker was sensor 6 — settled by stimulus (heated the suspect cluster, watched which zone moved). A copied mapping reads dead ⇒ suspect the numbering, settle by stimulus, not more copying.

## 3. Implement only with a promising, evidence-backed hypothesis

- **A reboot is yours to do when a channel exists** (ssh, USB gadget, fastboot): reboot yourself and continue. Reserve operator hands for what no channel reaches: battery pull, hardware key combo, moving media.
- **Invoke `find-docs` for build/image tooling before assembling** — kernel build system out-of-tree + config-fragment behaviour, `mkbootimg`/`mkdtboimg` header-version constraints for this boot-image layout, the distro's image builder (pmbootstrap, mobile-nixos, nix flake inputs) — current docs, not recalled flags; if not installed, the tool's own docs over the web. A flag recalled wrongly burns a full rebuild+flash cycle.
- **One variable per flash, falsifier before build.** State the hypothesis before flashing; write the falsifier before writing code: the smallest experiment that kills the plan either way, built first — one single module load returned the refusal that killed a 9.4k-line port premise. Order experiments by cost per information, not plan order: cheapest decisive experiment first.
- **Prefer runtime tests over reflashes:** tar-pipe files, unbind/rebind drivers, `insmod`. Seconds instead of minutes. But a probe leaves state: failed init can leave its platform device registered (every retry costs a reboot); a crashed probe can wedge the board into a physical power-cycle. Stage probe inputs, verify hashes host-side before firing, make it idempotent, expect one reboot per failed attempt. Staged inputs can persist across reboots and load stale against a new kernel — re-verify what you fire after any kernel change. Never probe through the channel the probe rebinds — one unbind/rebind test over that same USB link severed its own control channel.
- **Device-tree-only changes are cheap** — build just the DTB when the toolchain allows, then check the runtime surface, not just the build: a clean-building DT can still bind to nothing (one thermal driver registers one zone per sensor id and silently drops a duplicate — the zone list, not the build log, is the verdict).
- **Never edit-and-hope.** Read the exact current lines, write the exact replacement — no pattern-guessing then repairing your own syntax errors; announcing you're fixing your own broken edit has already cost a loop iteration, and on a port the sloppy edit can reach a flash before a build. Tool can't edit precisely ⇒ stop, re-read. Hand-repair of self-inflicted breakage is a defect, not a workflow.
- **Separate restructuring from upgrades.** Hold upstream version, patch content, config fixed while moving layers; compare built payloads before/after (one split preserved `Image` + `System.map` bytes). Upgrade separately. Verify downstream DTB + boot-image assembly paths too: kernel equivalence ≠ complete image still builds; a successful build doesn't identify what is flashed.
- **Start the patch battery pristine.** Fresh disposable tree at the exact intended upstream revision; check + apply each patch in series order so later checks see prerequisites. Never classify an apply failure as "already upstream" from a used working tree — one contaminated rebase check dropped a required header on that premise; the build failure forced restoration. Establish absorption from upstream code/history before retiring a patch.
- **A rebuild is the most expensive step in the loop — verify before paying.** A build dying 15 minutes in on a missing symbol taught what a 10-second host check would have; measured: four consecutive rebuilds burned on unchecked missing symbols. Before any full rebuild, run the cheap battery host-side: every patch applies cleanly to the exact tree (`git apply --check`); every referenced symbol is defined somewhere the patch sees (grep the tree — renamed upstream or in another dir kills the build late); every config option a patch/defconfig sets exists in this kernel's Kconfig (a nonexistent option is silently ignored — a clean config read is not evidence it took effect); compile touched directories/translation units first so the full build only runs on code that already compiled alone.
- **Build the artifact you selected; report per artifact.** One bundled job hid three of four finished targets behind a still-compiling patched desktop and reported only "still running". Select the target explicitly; keep progress + cancellation separate; status queries free of side effects — asking what is built must never start a build. A finished store output stays finished when a sibling is cancelled; only completed outputs are reusable.
- **Source preparation is transactional or it lies.** Derive readiness from the actual assembly, never a hand-maintained list — one helper searched for declarations the current flake no longer contained, applied zero of 47 patches, stamped itself ready. Apply each patch against the state left by its predecessors; missing files and check/apply failures are fatal; publish a success marker only after every step succeeded; fingerprint readiness on source identity + ordered patch contents so changed inputs report stale instead of reusing a tree. Partial/failed preparation must leave the previous ready tree usable.
- **After 3 refuted fixes: stop guessing, not stop working.** Three misses from the same failure model = the model is wrong; a fourth tweak from it misses too. Return to step 2 with wider scope — different stack layer, or the primary artefacts directly where precedent is absent — and return with findings stacked. Worked shape: five blind DT tweaks failed; the fix was five researched findings stacked — trustzone memory mode, vendor firmware paths, a host-capability quirk, the SMMU stream ID off the stock DTB, one property mainline made obsolete and dropped. No single tweak would have got there.

Before writing, recheck phase 0's handset/transport mapping, product, slot. **A deployment is a state machine, not one command.** Copying the closure, selecting the next-boot profile, switching the running system, booting = separate observed postconditions: a closure already present ≠ an activation; a matching profile symlink doesn't prove a prior activation completed; only a separately observed reboot marks the system booted — never flash or reboot automatically to make states agree. An explicit activation request reruns even when nothing needed copying. After deployment: verify the flashed payload by readback, reboot through the available channel, identify the running kernel, modules, intended system. Recheck boot-time init + required runtime functions: one upgrade lost sound-card registration to module coldplug ordering even though later manual init could work. Service readiness, silent playback, operator-confirmed acoustics are separate results; retain deferred/untested acceptance criteria explicitly rather than declaring them passed. Same honesty governs revalidation: on a required probe, empty output, timeout, or transport failure is a **FAIL, never a SKIP** — one checker scored a timed-out partial output as PASS and a dead transport as SKIP, then exited 0 — and a verification tool must never trigger an implicit build to obtain a missing image argument.

**Cleanup only after the new deployment passes its real reboot + runtime checks.** Inventory obsolete kernels, module trees, system generations, deployment roots, staging files. Preserve the running system, next-boot target, a complete known-good recovery path incl. dependencies — a saved boot image alone may not recover the system. Archive needed historical images, symbols, logs on the host before retiring device copies. Select retired deployments explicitly; remove through the distro's package manager or garbage collector — never manual deletion of managed files or blanket deletion of generations. Record space before/after, collector-reported reclamation, retained recovery targets. One port's operator reported substantial device-space recovery through GC with no precise total retained — total GC savings must not be attributed to kernels without separate accounting.
