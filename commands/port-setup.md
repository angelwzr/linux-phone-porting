Run phase 0 of the `linux-phone-porting` skill for: $ARGUMENTS

Runs once per port, before the first flash; re-check identity and capabilities when the device or transport changes. Do not flash anything during it. `SKILL.md` phase 0 owns the rules — boot-model class gates, backup rules, storage-health check, inventory fields, harvest targets, control-channel and convention requirements. This command adds the operator-questioning sequence and the reporting contract; it does not restate the rules.

**Establish the target.** Always ask the operator — every decision below is user-confirmed, never inferred. This holds no matter what already exists at or near the project: an initialized repo, a monorepo layer, a staged OS image, a prior agent-context file recording a "decision", a sibling device's configuration. Artifacts answer _what is present_, never _what is wanted_; one port's target OS was inferred from the surrounding workspace's layout and had to be superseded by the operator's actual selection. Offer what the artifacts suggest as options with trade-offs, get an explicit answer, and record it as user-confirmed — "the folder came with X" is not an answer to any of these:

1. Exact device identity: marketing name, internal codenames, OEM/ODM, SoC, regional/storage variant, EVT/DVT/PVT revision where known. Reconcile labels, bootloader identifiers, retail-OS properties and the stock board description; unresolved contradictions block choosing images. Sibling/prototype variants differ in panel, touch, modem.
2. Target OS/platform and release, required kernel lineage, service manager, hardware-service interfaces, build/image/update model, evidence/control tools — verified against the target project's current requirements; Linux-based does not imply mainline-compatible.
3. Target user interface/session: never assume a default; prefer the platform's supported stack.
4. Boot-model class first — retail-unlock, exploit-booted, or firmware-boot — then topology: slot and bank layout, active boot target, lock state where the concept exists. The class selects the write gate, backup route and board-authority artefact. Vendor banked A/B is not proof of seamless A/B; unavailable lock fields are unknown, not unlocked.
5. Existing backup: verify origin, acquisition method, coverage and hashes separately — a trustworthy download is not a device backup, and matching hashes prove integrity, not completeness or restorability. For prototype hardware a retail ROM is not a substitute for its own backup.
6. Custom recovery installed — convenience, not requirement.

**Demonstrated boot path required.** Retail-unlock: confirm the unlocked bootloader before any write-capable workflow; an unknown lock state does not pass; if locked, stop — no unlocking steps, point the user at their OEM's own instructions and resume once unlocked. Exploit-booted: require a payload boot path demonstrated on this device; no exploit-landing steps — point at the payload project's own instructions. Firmware-boot: require a demonstrated boot path. In every class the prerequisite is demonstrated capability, never a promised one.

**Take the backup** — every readable partition except userdata, per SKILL.md's backup rules: the userdata exclusion with its separate wipe authorization, device-unique partitions (modem NV/EFS, persist, calibration siblings) flagged to the operator as unreproducible and never published, private calibration in its protected runtime path, every image hashed beside the partition table. Where the class exposes no partitions, back up through the demonstrated route and record the coverage achieved. Confirm restorability before the first risky flash.

**Check storage health before trusting it.** Read the wear/lifetime report, record raw values and your interpretation; an unavailable field = unknown health (SKILL.md's storage rule explains why this gates every later I/O verdict).

**Inventory and harvest while stock is present** — per SKILL.md's inventory section: enumerate every component the stock system names against this variant's spec sheets (`find-docs`, `wigolo`; else plain web search), mark each claim declared/enumerated/driver-bound/exercised, and persist the component–wiring–document inventory with alternatives, unknowns and contradictions explicit. Readable retail beats a ROM image; privilege steps are the operator's — no rooting or jailbreaking steps; resume when access exists. From rooted stock, harvest the property dump, kernel config, vendor/odm trees, HAL/sensor configs, calibration artefacts and field-test modes. Ask whether a newer community custom OS exists and record the newest as an optional development source. A bootable retail OS stays a data-gathering channel — cross-check before transferring conclusions to mainline.

**Prove the control channels before choosing a build strategy** — SKILL.md's channel rules apply: discover and exercise the target's available tools (none individually mandatory), pin every command to a verified serial or transport, re-enumerate after mode changes, prove the boot/fetch/readback operations the proposed workflow needs before building for them, and exercise at least one post-boot channel into target Linux with its selector, address and demonstrated operations recorded.

**Lock the project to this ruleset.** Write into the project's agent context files (`CLAUDE.md`, `AGENTS.md`, equivalents): **all work touching this device goes through the skill's ruleset; no device action outside it** — phase 2 research, phase 3 gates, flashes only through the gates above. These rules are load-bearing, not advisory: a session that "just quickly" flashes outside them is how a backup-only-recoverable mistake happens.

**Mine it as a research source**, and tell the user what was found — per SKILL.md's research-value list: the stock board description for this class (record which artefact was obtained: boot-image DTB, ACPI tables, or vendor-kernel DT), firmware blobs and load order, vendor kernel cmdline and boot-image layout, the exact kernel version string that selects the GPL OEM release, and vendor sensor/modem/HAL configs.

**Set the conventions** per SKILL.md's working conventions: a demonstrated recovery path recorded; the optional layered layout (`kernel/<version>`, `soc/<vendor-soc>`, `os/<platform>`, `devices/<model>`) for multi-target workspaces — illustrative, never a rename order; everything large, private or device-derived under the gitignored `artifacts/` classes; per-device `logs/` with one subdir per boot/deploy and `LATEST-*` links; an artifact manifest mapping paths to class with origin, acquisition, coverage and hashes.

Report: the reconciled target identity, OS integration contract, intended interface/session and unresolved fields; backup provenance, coverage, integrity and restore evidence separately; the research artefacts extracted; the persistent inventory and linked document/acquisition records with unresolved gaps; hardware evidence levels; demonstrated transport capabilities and recovery limitations; and whether the retail OS remains available as a data-gathering boot.

**Then** phase 0 is done — it does not run again for this port. Ask the operator what should work first (the first capability to build or symptom to chase), enter the cycle at the matching entry point — `/evidence-sweep` for a failure, `/port-research` for a capability — and keep advancing under the skill's chain rule without waiting to be told the next step.
