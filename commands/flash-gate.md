Apply phase 3 of the `linux-phone-porting` skill to: $ARGUMENTS

**Precondition:** phase 0 identity, verified backup and demonstrated recovery/control capabilities are available, and phase 1 evidence or phase 2 capability research backs this change. Missing prerequisites return to their phase commands. Immediately before every device write, re-enumerate, pin the transport, reconcile target identity and active boot target with the intended artifact, and stop on ambiguity.

Answer each of these before anything is written to the device. Any "no" blocks the flash.

1. **What is the hypothesis?** State it as a falsifiable sentence — what is broken, why this change addresses it, and what the device will do differently if it is right.
2. **Which source backs it — and when was it found?** Name the evidence or the research finding, and say which research pass produced it. "It seems likely" is a refusal; so is a source that only comes from the ledger of earlier iterations when the current framing differs from theirs — after a refutation the backing must come from a pass that ran against the refuted framing, not the one it killed. A design derived from the vendor driver source or the stock DTB passes — naming the artefact is naming the source — but a _newly read_ part of it, not the paragraph a previous hypothesis already leaned on. That no distro has done this before is not a refusal; it is the normal case in bring-up.
3. **Is this one variable?** If the change touches more than one thing, split it. Keep a project/layout move separate from a kernel or OS upgrade: first compare the old and moved kernel, DTB, modules, firmware and initramfs payloads and downstream image-assembly inputs and outputs. Matching payloads alone do not prove an unchanged final boot image. A passing multi-variable flash teaches you nothing about which part worked.
4. **Can it be tested without a flash?** Push files with a tar pipe, unbind and rebind the driver, `insmod` the module, rebuild only the DTB. Seconds beat minutes; take the cheap test if one exists. A probe module leaves state — a failed init can cost a reboot per retry, and a crashed one can wedge the board — so stage its inputs, verify their hashes host-side, and expect one reboot per failed attempt.
5. **How many fixes have been refuted on this symptom?** Under `/port-loop`, the operator's refutation budget (5, 15, or unlimited, set at invocation) governs — the loop keeps going while budget remains. Standalone, past three the same-layer model is dead: do not flash a fourth tweak from it — widen the scope and re-enter `/source-sweep`, because the model of the failure is what is wrong.
6. **What result would refute this?** State the falsifier — the smallest experiment whose result kills the plan either way — and decide it now, so the next boot's dmesg is read honestly rather than for confirmation. Run the cheapest experiment that produces that result before flashing anything larger.

**If the change requires a full rebuild** — the most expensive step in the loop — run the pre-build verification battery before starting it. Start from a disposable pristine checkout of the exact prerequisite revision; check and apply the patch series in order, checking each patch against the state left by its predecessors, not each independently against the base. Then verify every referenced symbol is defined, every config option exists in this kernel's Kconfig (a non-existent option is silently ignored), and the touched directories or translation units compile alone. A build that dies 15 minutes in on a missing symbol is a check that was skipped, not bad luck.
**Before the battery: the edits themselves must be clean.** Changes are made by reading the exact current lines and writing the exact replacement — never pattern-guessed and then repaired after the first attempt broke the syntax. If a previous edit in this session is being "fixed" or "repaired", stop and redo that edit from a fresh read instead of patching over it; a broken intermediate state that happens to build is worse than one that does not.

If all six pass and prerequisites remain satisfied, apply the cheapest decisive experiment, then record the outcome against the hypothesis as stated — including, on a refutation, what it rules out. When a reboot is needed and a control channel reaches it, reboot through that channel; request operator hands only for unreachable actions. Name the action and direction, then verify an observable result. For disappearance, observe the drop as an event or obtain done-confirmation plus a failing probe; silence alone is ambiguous. Poll briefly and re-ask within a bounded wait.

Read the runtime surface the change was meant to move: a DT that builds can still bind to nothing. Record reboot completion and transport/service readiness separately from end-to-end acceptance; only exercising the requested capability satisfies the latter. Capture before/after metrics under the same controlled conditions through `/evidence-sweep`.

**Post-upgrade cleanup is gated by a verified reboot and required runtime checks.** After both pass, inventory disk use, generations, boot entries and dependencies. Preserve the running system, the selected next-boot system and a complete rollback set including its dependent kernel, modules, firmware, initramfs and userspace closure. Archive required historical images, symbols and logs on the host before retiring device copies. Only then remove explicitly identified obsolete deployments through the distro's package manager or appropriately rooted GC, never by manually deleting managed files; no blanket deletion of caches, generations or artifacts. Record filesystem space before/after, collector-reported reclamation and retained recovery paths. Do not attribute total GC savings to old kernels without separate accounting.

**If the defect is shared, prepare a portable upstream report:** exact base and patched revisions, configuration, expected versus observed behavior, captured reproduction and boundary conditions (including nearby passing/failing cases where measured). Separate device-specific facts from the shared defect. Cite a CVE only when its affected/fixed source and preconditions match; keep uncertain applicability qualified. Track submitted, accepted, merged and released as distinct states, with evidence for each.
